# 协作开发指南（两个人以上）

> 小程序协作比普通前端项目多三个坑：**云开发环境是共享的**、**云函数谁部署谁覆盖**、**AppID 有权限校验**。
> 这份文档把约定写死，照着做就不会互相踩。

---

## 一、开始前（一次性，约 20 分钟）

### 1. 小程序后台加开发者

微信公众平台 → 登录你的小程序 → **管理 → 成员管理 → 开发者** → 添加室友的微信号。

> ⚠️ 不加的话，室友即使拿到了代码也**编译不了**——微信会校验 AppID 和当前登录账号的权限关系。
> 添加后室友用**自己的微信**登录开发者工具，就能打开这个项目。

### 2. 建 GitHub 私有仓库

**必须选 Private**。虽然密钥已排除，但 `project.config.json` 里有 AppID、代码结构也会暴露。
私有仓库的协作者数量不限，免费。

创建时**不要勾选** Add a README / .gitignore / license（会和你本地历史冲突）。

### 3. 推上去

```bash
cd luguan-dorm
git remote add origin https://github.com/userna9/self-discipline-dorm.git
git branch -M main
git push -u origin main
```

然后 GitHub → Settings → Collaborators → 邀请室友的账号。

## 二、室友第一次跑起来

```bash
git clone https://github.com/userna9/self-discipline-dorm.git
cd luguan-dorm
```

### 关键：OSS 密钥不要给室友

`cloudfunctions/ossSign/config.js` 被 `.gitignore` 忽略了，克隆下来**没有这个文件**。

**推荐做法：用云开发控制台的环境变量，谁都不用碰密钥。**

云开发控制台 → 云函数 → `ossSign` → 配置 → 环境变量，添加：

| 变量名 | 值 |
|---|---|
| `OSS_REGION` | `oss-cn-wuhan-lr` |
| `OSS_BUCKET` | `my-first-bucket-996` |
| `OSS_AK_ID` | 你的 AccessKey ID |
| `OSS_AK_SECRET` | 你的 AccessKey Secret |

代码里环境变量优先级最高，所以 `config.js` 缺失也能正常跑（`index.js` 里做了容错，不会崩）。

> 只有需要改 OSS 配置的人才需要本地建 `config.js`：
> `cp cloudfunctions/ossSign/config.example.js cloudfunctions/ossSign/config.js`

### 然后用开发者工具打开

导入项目 → 选 `luguan-dorm` 目录 → AppID 会自动读取 `project.config.json` 里的。
第一次打开会自动生成 `project.private.config.json`（个人配置，已被忽略，不会互相覆盖）。

## 三、日常协作流程

```
main        ← 永远可运行，不直接往上推
 └ feature/xxx   ← 每人一条分支，开发完提 PR
```

```bash
git checkout -b feature/comment-like
# 改代码...
git add -A
git commit -m "feat: 评论支持点赞"
git push -u origin feature/comment-like
```

然后在 GitHub 上开 Pull Request，另一个人看一眼再合并。

**每次开始改之前先同步**：

```bash
git checkout main
git pull
git checkout -b feature/xxx
```

### 提交信息建议

| 前缀 | 用途 |
|---|---|
| `feat:` | 新功能 |
| `fix:` | 修 bug |
| `style:` | 只改样式/格式 |
| `docs:` | 只改文档 |
| `refactor:` | 重构，不改行为 |

## 四、分工建议：按目录切，别按功能切

冲突的根源是**两个人改同一个文件**。最省事的切法：

| 谁 | 负责范围 |
|---|---|
| A | `miniprogram/pages/index`、`miniprogram/pages/profile`、`miniprogram/utils` |
| B | `miniprogram/pages/moments`、`miniprogram/pages/checkin`、`miniprogram/pages/lottery` |
| 共用 | `cloudfunctions/`、`app.json`、`app.wxss` —— **改之前先在群里说一声** |

---

## 五、云函数：约定一个人部署

**这是最容易出事的地方。** 云开发没有"预发布环境"，谁点「上传并部署」，线上立刻变成谁的版本。

👉 **约定：云函数只由 A 统一部署。**

B 改完 `cloudfunctions/` 下的代码 → 提交 → 告诉 A → A 拉代码后部署。
如果两个人都部署，很容易出现"我明明改了却没生效"——因为被对方覆盖了。

**判断线上跑的是不是最新版**（以 `ossSign` 为例）：云端测试传 `{"action":"xx"}`，返回里带 `"version"` 就说明是新版。

## 六、数据库是共享的（重点）

免费版云开发**只有一个环境**，两个人连的是**同一个数据库**。这意味着：

- 室友测试发的动态、打的卡，**其他 4 个人都能看到**
- 测试时删数据要小心，别把真实数据删了
- 两个人同时改同一条记录，后写的覆盖先写的

### 建议的约定

1. **测试内容加标记**：测试动态就写「测试勿理」之类，测完自己删
2. **不要批量删集合**：清理测试数据时用 `where` 精确删，别用「清空集合」
3. **改数据结构前先说**：比如给 `comments` 加字段，两人要同时知道

> 想彻底隔离，只能升级云开发付费套餐开第二个环境——宿舍项目没必要。

## 七、冲突高发文件

| 文件 | 为什么容易冲突 | 怎么办 |
|---|---|---|
| `project.config.json` | 开发者工具会自动改写（编译设置、libVersion） | 尽量别手动改；冲突了保留双方的差异项 |
| `app.json` | 两人同时加页面 | 加页面前先说；冲突时手动合并 pages 数组 |
| `app.wxss` | 全局样式，谁都想加 | 新样式优先写在页面自己的 wxss 里 |
| `cloudfunctions/*/index.js` | 两人改同一个函数 | 按函数分工，别两个人同时改一个 |

### 冲突了怎么处理

```bash
git pull --rebase
# 出现 CONFLICT，打开文件，找 <<<<<<< ======= >>>>>>>
# 手动改成最终版本，删掉冲突标记
git add 冲突的文件
git rebase --continue
```

**不要慌着 `git checkout -- .`**，那会把你的改动全丢掉。

## 八、常见问题

| 现象 | 原因 | 解决 |
|---|---|---|
| 室友打不开项目，提示无权限 | 没加开发者 | 后台「成员管理」加微信号 |
| 云函数报 `OSS 配置缺失` | 环境变量没配 | 控制台给 `ossSign` 配 4 个变量 |
| 改了云函数但没生效 | 别人覆盖了 / 没部署 | 约定一人部署；用 `version` 字段确认 |
| `git status` 里出现一堆 `project.private.config.json` | 没被忽略 | 本项目已忽略，若出现说明克隆的是旧版本 |
| 推送被拒 `non-fast-forward` | 远端有别人的新提交 | 先 `git pull --rebase` 再推 |
| 提示 `index.lock` 已存在 | 上一次 git 操作被中断 | 确认没有 git 进程后删除 `.git/index.lock` |

---

## 九、一句话总结

> **代码走分支 + PR，云函数一人部署，数据库改动先打招呼，密钥不进仓库。**

做到这四条，两个人协作基本不会出事。
